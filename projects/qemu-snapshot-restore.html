QEMU snapshot restore

A fuzzer that tests a whole virtual machine has to put it back in the same state after every input. We built a harness that drives a QEMU guest entirely from the host and measured five ways of restoring a snapshot, from full reload to copy-on-write, to find which one gives the most test cases per second, and when.

ποταμοῖσι τοῖσιν αὐτοῖσιν ἐμβαίνουσιν ἕτερα καὶ ἕτερα ὕδατα ἐπιρρεῖ.

“Upon those who step into the same rivers, different and again different waters flow.”

Heraclitus, fragment B12 (Diels–Kranz)

B12 is held to be closer to Heraclitus’ own words than the famous “you cannot step twice into the same river” (B91, through Plato). Snapshot fuzzing wants exactly what he denies: the same river every time. A restore makes the waters the same again, and its cost is how much water has changed.

αʹThe problem

Snapshot-based fuzzing reaches an interesting program state once, freezes the whole VM there, then replays thousands of mutated inputs from that exact state. Between two inputs, the VM must be restored. If one restore takes 500 ms, the fuzzer can never run more than 2 test cases per second.

QEMU’s classic loadvm reads the entire snapshot and copies every page back into guest RAM, so its cost is O(guest RAM), even when the guest only changed a few megabytes. The goal was to measure strategies whose cost follows what the guest actually dirtied instead.

The key choice was the metric: total iteration time, execution plus restore. A strategy can look fast at restore time and push its cost into the next execution; measuring restore alone would have hidden exactly that.

What the harness measures

The host controls everything: breakpoints and memory writes over QEMU’s built-in GDB stub, process control over the guest agent. The guest target waits at A, receives N dirty pages, writes one byte to each, and reaches B.

Each restore is broken down with kernel accounting, so a slow restore can be attributed to the disk, the CPU or the scheduler.

The finding that generalises

The crossover depends on the absolute amount of dirty data in MB, not on the dirty fraction of RAM. A fuzzer dirtying 100 MB of a 512 MB guest and one dirtying 100 MB of a 4 GB guest should pick the same mode.

δʹLimits

  • Synthetic writesThe target dirties the first N pages in order, the most cache-friendly pattern. A real fuzzer writes all over memory, which would hurt hotreload-wb more than hotreload-shm.
  • Warm page cacheRuns were on a lightly loaded 128 GiB host. Under memory pressure, cached snapshot pages get evicted and the SSD-backed modes slow down.
  • I/O time is a residualComputed as wall − CPU − run-queue wait; any unmeasured overhead lands there, so it is an upper bound.
  • Two machinesThe crossover moved 3× between the server and the laptop. Thresholds must be measured on the target hardware.
  • Open questionHotreload still pays a small cost that grows with RAM even at zero dirty pages (≈ 75 ms from 512 MB to 4 GB), probably from structures sized to the whole guest.
