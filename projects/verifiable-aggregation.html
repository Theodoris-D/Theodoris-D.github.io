Verifiable secure aggregation

In federated learning, a server adds up the model updates of many users. Here the server never sees a single update, only their sum, and it cannot lie about that sum: anyone holding the public verification key can check it with two sides of a pairing equation.

αʹThe problem

Secure aggregation hides each user’s data from the server. It usually trusts the server to report the sum honestly. That is a weak point: a server that drops users, double-counts them or nudges the result can steer a federated model, and nobody would know.

PUDA (Private User Data Aggregation, CANS 2015) answers both concerns at once for a single value per user: encryption masks cancel out in the sum, and a homomorphic tag lets anyone verify it. Federated learning needs vectors, one coordinate per model parameter. This project extends the scheme to vectors of dimension κ and adds a key-binding scheme so a user only obtains a valid tag from the tagger if both hold the same key.

Three properties, three tests

Correctness — the aggregated sum equals the plaintext sum, exactly.

Completeness — verification always accepts an honest aggregate.

Soundness — verification rejects a sum with one tampered coordinate.

Each is a property test run 100 times with random users (2–20), dimensions (1–5) and data.

βʹThe protocol

How the masks cancel

User i encrypts coordinate k of its vector by adding a mask derived from the round identifier τ and its own key. The aggregator’s key is the negated sum of every user’s key, so in the sum all masks vanish and only P₁ · Σ x_ik remains. A lookup table of 216 precomputed points then recovers the integer sum (a small discrete logarithm).

How anyone can check

Each user also sends a tag that commits to its whole vector with the shared secret a and its own b_i. Tags add up like the data. Pairings turn the check into public information: the verifier needs only vk, the published sums and τ.

Key binding (KBS)

Two rounds, built on a 2HashDH oblivious PRF. The tagger encrypts the blinded tag under a key derived from its OPRF key; the user can only decrypt it, with AES-256-GCM, if its own key matches. With mismatched keys, decryption fails and the user gets nothing.

# EncTag — user i, round τ, coordinate k
c_ik    = P₁·x_ik + H(τ‖k)·ek_i
σ_i     = H(τ)·b_i + (Σ_k a_k·x_ik)·P₁

# Aggregate — untrusted server
V_k     = Σ_i c_ik + H(τ‖k)·ska      // ska = −Σ ek_i
        = P₁·Σ_i x_ik
x_k     = DLP(V_k)                   // 2¹⁶-entry table
γ       = Σ_i σ_i

# Verify — anyone
e(γ, P₂) =?  Π_k e(P₁·x_k, vk_a[k])
             · Π_i e(H(τ), vk_b[i])

γʹPerformance

Total time, all 24 configurations

The discrete-log table

The aggregator recovers each integer sum from a point P₁ · x with a precomputed table. The table bounds what can be summed: with 216 entries, users × max value must stay below 65,536. I measured how far it could grow on a laptop before memory ran out.

About 60 bytes per entry: a 48-byte compressed G₁ point, an 8-byte integer, and hash-map overhead.

δʹLimits

  • KBS is a prototypeThe user’s zero-knowledge proof in round 1 is simulated, so a malicious user is not yet ruled out.
  • Trusted dealerSetup assumes one honest party generates and distributes every key.
  • Bounded sumsWith a 2¹⁶ table, users × max value must stay below 65,536: fine for quantised updates, not for raw floats.
  • Noisy timingsOne machine, averaged trials; some series are not monotone (e.g. aggregation at κ = 100), so read trends, not single cells.
  • No dropoutsEvery user who received keys must contribute, since the aggregator key cancels exactly the sum of all masks.
